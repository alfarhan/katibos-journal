# katibOS

Arabic-first (RTL) distraction-free writing firmware for ESP32-S3 e-ink/reflective-LCD typewriters. C++ / Arduino / PlatformIO. Code is in `firmware/`.

## One board

**MicroJournal rev_8** is the only target: ESP32-S3, 400×300 ST7305/ST7306 reflective LCD, and the built-in **matrix keypad** (`KEYPAD_68`) wired straight to the chip — no BLE keyboard, no USB-serial typing, no battery sense line. A second board (Waveshare ESP32-S3-RLCD-4.2) was supported until 1.12.2 and has been removed; if you find a `#ifdef` guarding "the other board", it is a leftover, not a contract.

| Env | Notes |
|-----|-------|
| `microjournal` (default) | the board, panel profile **`RLCD_TYPE=1`** |
| `microjournal_type2` | same board, the other supplier's panel |

**The panel profile is load-bearing.** rev_8's glass is a **YDP420H001-V3** — 300x400 dots, ST7306, normally-white reflective (confirmed from the supplier drawing; the AliExpress listing's "320x320" is wrong). That is the driver's **type 1** profile, and `platformio.ini` sets `-D RLCD_TYPE=1` explicitly, because the library header ([`ST7305_4p2_BW_DisplayDriver.h`](firmware/lib/ST7305_MonoTFT_Library/src/ST7305_4p2_BW_DisplayDriver.h)) defaults it to **2** — a different panel (400x300, 1bpp packing, a narrower column window). Under the wrong profile the frame is written to part of the glass only, and the band that is never addressed keeps whatever was there: it survives a reboot, a reflash and a **full chip erase**, which makes it look exactly like burn-in. The tell is that the device's own live status bar sits *part-way up* the screen with a stale one below it — **a live frame that doesn't reach the bottom is geometry, not retention.** Don't chase it as image sticking. Both envs restate `${flags.base}` and pick the profile themselves; PlatformIO reorders and de-duplicates `build_flags`, so a trailing `-D`/`-U` can't be relied on to override an inherited one.

**Type 1 packs 2 bits per pixel, four pixels per byte** — 30000 bytes × 4 = 120000 = exactly 300x400, so `writePhysicalPoint` selects the 2-bit field with *both* `px & 1` and `py & 1`. It used to write a whole `0x0F` nibble keyed on `px & 1` alone, throwing the low bit of `py` away: `py` and `py+1` collided in one nibble and the second write won. Since `py` is the UI's **x**, that drew 200 columns across a 400-column screen and doubled every vertical stem — Arabic went soft and alef-lam came out visibly the wrong width while horizontals stayed clean. If rows ever come out combed, the py-parity term is inverted; which 2-bit field is the even row is the one guess in that function. This is **not** a grayscale question: `0xB9 = 0x20` puts the panel in Mono mode under *both* profiles, so "the text looks soft" is never about bit depth here. Type 2's packing is a genuine 1bpp 2x4 block per byte at full 400x300 — on rev_8's glass it renders sharply but reaches only the top band, which is why the fix was type 1's geometry plus per-pixel resolution rather than switching profiles.

**Blackness is stroke width, not voltage.** A single dot barely darkens this reflective panel; two adjacent dots go properly black. The stock rev_8 firmware looks blacker than katibOS did for exactly one reason — its half-width packing drew every stroke on two dots — and its drive voltages, frame rate (`0xB2 = 0x05`) and init sequence are byte-identical to ours, so there is nothing to tune there. Don't go hunting contrast registers. The two properties are independent: **Bold** gets the weight back with `setEmbolden()`, which widens ink one pixel at native size, so stems land on two dots while still being free to start on odd columns. It widens **ink only, and leftward** — in opaque mode (`setFontMode(0)`, what the editor uses) a background run starts exactly where the ink run ended, so a rightward extension is overdrawn by the very next run and silently vanishes. Bold used to be a smaller face doubled via `setScale`, which also gave 2px stems but cost twice the glyph and with it lines and characters per line; it is now Normal's own faces emboldened, same size and layout. **Embolden reaches editor text only** — it is wired into `WP_selectFont`, so no menu screen sees it: the home screen renders byte-identically with Bold on or off (14817 black pixels either way, measured in the emulator). Every menu label, frame, divider, scrollbar and icon therefore went from 2-dot strokes to 1-dot with the packing fix and cannot get the weight back from the font setting. Left that way deliberately — menu text is 1-dot on stock rev_8 and upstream too, and only editor weight was ever the complaint. If menus ever do read faint on the glass, the fix is a default that `setFont` resets *to* instead of to zero, not a call-site sweep.

**Vertical thickening was tried and rejected — on the glass, not on paper.** `setEmbolden()` widens ink in **x only**, so under Bold no stroke is left 1px wide but 1px-*tall* strokes survive, and in Arabic those carry the baseline joins and the flat bowls of ب/ت/ث. Measured in the emulator on a page of Arabic: Bold leaves 0.0% of strokes 1px wide against 3.3% 1px tall. Drawing each glyph a second time one row up in transparent mode (`setFontMode(1)`, upward because lines are drawn top-to-bottom and ink placed *below* is erased by the next line's opaque background box) took that to **0.0% in both axes** — geometrically a clean sweep. It still looked worse on the real panel and was reverted (2026-08-16). Two things that measurement did not capture: naively thickening everything merges the harakat into their letters, since the channel between them is exactly the one pixel being eaten — visible immediately on vowelled text at Compact spacing, and only partly fixed by skipping the pass for marks and for any base carrying one; and the logical framebuffer is not what the eye sees, which is the whole reason this problem exists. **Don't re-derive this from the pixel counts — they say it works.**

**Greyscale needs a different pixel format, not a gamma byte (settled 2026-08-19 from the ST7306 datasheet).** `0xB9 = 0x00` (4GS instead of Mono's `0x20`) looks one byte away and is not: five candidate memory layouts were swept on the glass (branch `gs-test`, since deleted) and all failed - Mono's own 2x2-dot-block-per-byte and its px/py swap duplicated the frame 2x, three plane-split variants 4x. The datasheet says why. **ST7306 §7.4: "The single RAM cell of this chip is 24bits and the data for 4/6/8/24 pixels (64color/16color/8color/mono) is collected"** - one column address is always 24 bits, and bits-per-pixel is a *format*, not a gamma: mono 1bpp (24 px/cell), 8color 3bpp, **16color/16gray 4bpp (6 px/cell)**, 64color 6bpp. There is no 2-bits-per-pixel mode, so no rearrangement of a Mono-shaped frame can ever produce grey. The greys themselves are **fine** - a solid mid-tone came out clean on the glass, no dither, no shimmer; don't re-ask that. §7.2.3's map also explains type 1: each page address drives **two lines**, 24 px per cell, so Mono for this glass is 25 columns / 15000 bytes - exactly *type 2*, and what Framework's driver (`github.com/FrameworkComputer/st7306-rs`), the osptek vendor demo and the MicroPython driver all send. rev_8's working type 1 sends **double** that, writing each dot twice; correct on this glass, but off the standard path, which is why type 2 reaches only part of it. The 4bpp route was then **spiked on the glass and rejected (2026-08-19, branch `gray16`, deleted)**. §7.2.2 mapping (2) gives the exact packing - one 24-bit cell carries **six pixels of four bits, all on one line** (Pix1 = P1..P4, Pix2 = P5..P8; §7.2.1 TYPE2 puts P1 at D7 of the cell's first byte under BPS=1) - and it renders: a 16-step ramp came out with **eight to ten clean, distinct levels, no dither and no shimmer**, diagonal and mid-grey patches intact. What kills it is coverage. 50 cells x 6 px x 200 rows is **60000 pixels against this panel's 120000 dots**, and on the glass the frame duplicates side by side with only part of the ramp in each copy - the same failure the Mono-shaped attempt showed, for the reason the arithmetic predicts. So grey on this board costs **half the resolution**, which is exactly the regression the type 1 packing fix cured (half-width columns, alef-lam the wrong width, Arabic soft). No amount of anti-aliased font work downstream buys that back. **Settled, not abandoned: don't re-spike the greys (they work) and don't re-spike the geometry (it halves).** **The cheap answer to jaggedness is rasterisation, then Bold** - see below.

**Rasterisation beats typeface at this size (2026-08-19).** Fouad compared IBM Plex against Plex Text/Med, Vazirmatn and Noto Sans on the panel and kept IBM Plex, so the remaining lever is how the outline becomes pixels. Measured over every FE70-FEFF glyph of each candidate BDF: **hinting is what adds the artifacts** - at px21 the hinted face leaves 4 isolated single pixels where unhinted leaves 0 (10/8/12 at px18/19/20), with slightly fewer staircase steps per unit of ink (0.467 vs 0.476) and a *narrower* advance (12.10 vs 12.50), so it costs nothing in layout. `otf2bdf -n` turns hinting off. Size helps monotonically (steps/ink 0.476 at px21 -> 0.412 at px23 -> 0.379 at px25) but paragraph height must stay <= pitch-2 or Compact spacing clips, which makes **px23 (para 20) the largest usable Normal**. Shipped as three faces of the same typeface at the same weight: `ibmplex` (px21 hinted, what shipped before), `plexclean` (px21 unhinted), `plexbig` (px23 hinted, ~10% fewer chars per line). `config.arabic_font` is now the family **index** into `WP_ARABIC`, not a 0/1 toggle; 0 (stock 10x20) and 1 (IBM Plex) keep their meaning so old configs land where they did. Regenerate with `otf2bdf + bdfconv`, map `32-126,$600-$6ff,$fe70-$feff` (bdfconv wants `$` for hex, and the ASCII range is what gives the header its ascent/descent fields - Arabic-only yields para height 0).

**The editor's Arabic face is IBM Plex Sans Arabic** — `ibmplex_arabic_m` for Normal, `_l` for Large, `_m` emboldened for Bold; Latin stays ProFont. **Any Arabic font here must cover FE70–FEFF**, the presentation forms `bidi::layoutLine` emits: a font carrying only the base 0621–064A block renders a blank for every shaped letter, which looks like the shaper failing rather than the font. The three faces were built with `otf2bdf + bdfconv` for exactly that coverage, so regenerate them the same way rather than converting a TTF naively. Pitch comes from the faces' *paragraph* heights (19/22 for `_m`/`_l`, in bytes 15/16 of each u8g2 header), not `maxH` — that is 31/38/43 because stacked harakat blow up the glyph box, and Compact line spacing is where vowelled text touches first. One knowingly-open thing: this is IBM Plex's **Bold** weight with no Regular in the set, so Normal is heavier than the old `10x20_t_arabic` and Bold is a bold face emboldened again. There was a third face, `_s`, that no profile ever selected; it is gone from `u8g2_fonts.c` now. Note it was **never costing flash** — each face sits in its own `U8G2_FONT_SECTION` and `--gc-sections` had already been dropping it, so measure before assuming an unreferenced font array is weight on the device.

**`display()` sends only the rows that changed.** `writePhysicalPoint` widens a dirty span, but only when a pixel's value actually *changes* — the editor re-blits the whole page every tick, so tracking pixels *written* would mark everything and save nothing. A redraw that reproduces the same frame sends zero bytes and the panel just keeps refreshing from its own RAM. The span is in buffer rows because that axis is free: the buffer is row-major in `real_y` and type 1's `0x2B` window is 0..199, exactly the `real_y` range. `clearDisplay`/`fill`/`setInvert` all mark everything dirty — `setInvert` especially, since every sent byte flips while the framebuffer never moves. Type 2 always sends full frames; its buffer is column-major, so its rows are not the window's rows. Keep the payoff in proportion, though: this saves ~6ms of SPI against the ~60ms of BiDi shaping, glyph measurement and page blit, and `blinkPhase` in `WP_contentChanged()` still drives that whole path twice a second while idle.

**A flash is a soft restart, not a power cycle.** `esptool` resets the ESP32 via RTS; the panel's supply is never interrupted. So reflashing cannot clear panel state, and "it looked fine after I flashed it" is not evidence about anything that survives a warm restart. The **depolarizing flush** in `display_RLCD_setup` is what clears it: this glass is normally-white reflective, a long-held frame traps DC bias in the liquid crystal, and rewriting white does *not* lift it — the charge only relaxes while the pixel is driven the other way. Symptom is the whole panel coming back grey and washed out after any soft restart (including the reboot at the end of an OTA), fixed only by pulling the cable. It is **not** the LPM/HPM init sequence; that was blamed twice and fixed twice, wrongly. Don't remove the flush.

`BOARD_NAME` is shown at boot in serial and on the About screen.

## Build / flash (from `firmware/`)

```
pio run -e microjournal                                 # build
pio run -e <env> -t upload --upload-port <PORT>         # flash (e.g. /dev/cu.usbmodem1101)
pio device monitor -e <env> --port <PORT>               # 115200, exception_decoder on
```
Upload fails "port busy" if a monitor is open — close it first.

## Where things live

- **`totalLine` is the INDEX of the last line, not a count.** `Editor` starts it at 0 and increments per break, and `WP_line_bytes` treats `line_num == totalLine` as valid. The renderer skipped `line >= totalLine` and gated its neighbour repaint on `cursorLine + 1 < totalLine`, so the document's final line was drawn only while the caret sat on it - which in Bottom flow it always does, hiding the bug, while Top/Middle simply lost the line (fixed 2026-08-19).
- **The viewport holds; it does not pin.** Bottom text flow used to be `topLine = cursorLine - lastRow` outright, so the caret owned the bottom screen row and pressing Up scrolled the document down - the line you had just written fell off the bottom, and nothing below the caret was ever visible. `editorTopLine` now holds the window while the caret is inside it and scrolls only when the caret leaves, keeping the pin for the case it existed for: appending on the document's last line (`EDITOR_TOP_UNSET` seeds the first render so a freshly opened file still bottom-anchors). Host tests in `tests/test_editorviewport.cpp` cover all three transitions.
- **Typing speed is a render-count problem, not a drawing problem (measured on-device 2026-08-22).** Stock upstream firmware types perfectly on the same panel, which is how this was cornered - the glass was never the limit. Three costs, all found with the `RLCD_PERF` probe (env `microjournal_perf`: logs gap/render/push per tick, plus a clear/text/status/cursor split): the **500ms caret blink counted as a content change**, so it rebuilt the whole page - BiDi layout, per-glyph measurement, three-line blit (34ms) plus the status bar (16ms) - to reproduce a frame the panel already held, twice a second forever and once between every pair of keystrokes (idle render **57ms -> 1ms** once a blink-only tick repaints just the caret bar); the **status bar redrew on every keystroke** though nothing in it had moved, and it owns the sync/AI/SAVED toasts, which run on their own timers rather than off any compared value, so it must stay dirty while one can be on screen; and `WP_selectFont` called `setFont` (which re-reads the face header) **twice per cell plus once per mark**, while `WP_render_line` measured every cell twice - once to total the line width, once to draw it. Read u8g2's own live state when skipping a `setFont`, never a shadow copy, or a `setFont` from the status bar leaves it stale.
- **`updateScreen()` re-wraps from the edited line, not from byte 0.** "A new file is perfect, a 400-word file is slow" was the tell: the wrap measures each character, and for Arabic `WP_measure_char_at` shapes a **whole word per call**, so a full rebuild re-shaped every word in the window on every keystroke. Wrapping is greedy and left to right, so an edit cannot change how any line *before* it breaks - `updateScreen(fromPos)` restarts at the line holding the edit with one line of margin, and only the typing path passes a position (everything else still rebuilds). Verified by rendering a 312-word Arabic file after typing and diffing the frame against a forced full rebuild: byte-identical. **Still outstanding:** autosave runs inside the render (`WP_check_saved()` -> `saveFile()` writes flash synchronously ~2s after the last keystroke), which stalls the screen up to ~1s.
- **Editor text is drawn ink-only where it can be.** u8g2's opaque mode (`setFontMode(0)`) paints each glyph's own background box, and that box is the *face's* full height - 37-40px on the Arabic faces - so it overruns every line pitch, not just Compact's `font_height - 2`. On a full repaint the panel is already cleared, so the whole page draws in transparent mode; the partial path still needs opaque for the caret line (it repaints over its own previous frame) and therefore re-draws the two neighbours transparently afterwards to put back the rows the caret line's boxes ate. Symptom when this is wrong: letter bottoms vanish while typing and return on the next full repaint.
- **Editor core** (`service/Editor/`) — driver-agnostic; buffer, undo, selection, wrapping. Shared by all fronts, so keep changes driver-neutral.
- **Renderer** (`display/RLCD/WordProcessor/`) — draws the editor. `display_RLCD_core()` returns 0 → render runs on core 0 with input (avoids a cross-core buffer race that panicked on fast typing).
- **One board means one set of guards.** `keyboard.cpp` used to branch on `REV5`, `REV6`, `REV7`, `CARDPUTER`, `KNOB`, `KEYPAD_48` and `BOARD_PICO`; every one of those `#include`s pointed at a directory that no longer exists, so the branches could not have compiled even with the macro defined. They are gone, along with the RP2040 filesystem/mass-storage files and `main.cpp`'s Pico-only `setup1`/`loop1`. `KEYPAD_68` is the only keyboard guard left. If you are porting to a second board, start from git history rather than from a `#ifdef` you find here.
- **Input** (`keyboard/`): `keyboard.cpp` is HID/dispatch (still the path for any external HID keyboard and the one the emulator drives); `Keypad/68/Keypad_68.cpp` is the matrix scan; `Locale/` holds the layout tables — `keyboard_us_equivalent` reverses a localized letter to its US base for layout-independent menu shortcuts, and `INT` is the US table plus dead-key composition, where the matrix path must feed the *resolved* character to `keyboard_precursor_filter` (the dead keys sit on punctuation, which has no `key_hid` entry, and half of them live on layers a physical-key lookup can't see) — the HID path gets that free via `keyboard_keycode_ascii`.
- **Editor commands** map to shared action codes (`SEL_*`, `COPY`, `SELECTALL`, …) in `display/display.h`, delivered by HID keycode.
- **AI proofread** (`service/Ai/`) — **Ctrl+G** in the editor sends the OPEN FILE to Gemini for a proofread (grammar, spelling incl. hamza + taa-marbuta/haa, punctuation) and replaces it. The prompt is Fouad's own wording, kept **verbatim** in `AI_PROMPT` — it *is* the spec, so don't paraphrase it; note it asks for hamza/taa corrections and forbids rephrasing or word substitution. Prompt and document go as two separate `parts`, so no in-band marker can collide with the text. Key/model/endpoint in `config.json` under `ai` (`key`, optional `model`, optional `url` for a local stand-in). Works on the file, not the editor buffer — the buffer is only a sliding window (`loadWindow`), so the document isn't in RAM. Runs as an `app["task"]="ai_correct"` pass pumped by `ai_loop()` on the background core, like sync; each stage marks the screen dirty since nothing renders while it blocks. Three guards, all learned the hard way: the reply is **refused** if it's under half or over double the original length (a model that rewrites or prepends commentary), the original is moved to `<file>_backup.txt` before the swap (the replace is far too big for the 2KB undo arena, so **Ctrl+Z cannot undo it** — the backup is the way back), and fence-stripping trims *exactly* the fence newlines rather than calling `trim()`, or it silently eats trailing blank lines the writer meant to keep. Capped at `AI_MAX_BYTES` (24KB) since request + reply are both in RAM.
- **Wi-Fi selection** (`service/Net/`) — `net_connect()` is the ONE place that brings the radio up; sync, OTA and AI proofread all call it (there used to be four copies, which is how the AI path shipped missing the post-association settle delay the sync path already had). Order: the **pinned** network (`config.wifi_pref`, set with **D** on the Wi-Fi screen and marked there with a checkmark — a standing choice outranks history), then the SSID that worked last (`config.wifi_last`), both **with no scan** — the common case, ~2s — then saved networks seen in a scan **strongest-RSSI first**, then saved networks absent from the scan (hidden SSIDs, which scan-then-match can never find). Forgetting a network clears a pin on it, or `net_connect` would keep skipping a network it can never join. Bounded: 6s per attempt, 24s total. The reachability probe then separates "no Wi-Fi" from a network that won't carry the traffic: it resolves the host first and reports **"no DNS"** or **"no internet"** accordingly, twice a second apart, since a hotspot's resolver is often still settling when the lease lands. Measured on Fouad's phone hotspot: DNS is fine there, TCP to :443 times out ~7 attempts in 8, and the one that opens still fails the TLS handshake — so **don't raise `NET_PROBE_MS` to "fix" it**, that just moves the failure back to the bare `start_ssl_client: -1` the probe exists to explain.
- **Idle throttle** (`service/Idle/`) — after `config.idle_secs` (default 60, Options → Power save) with no keypress, the main loop `delay(30)`s instead of spinning; any key restores it via `idle_touch()` in `display_keyboard()` (the single input funnel). The panel is deliberately **left in High Power mode**: this panel's `Low_Power_Mode()` keeps refreshing the held frame at the wrong drive voltages and the text visibly rots while you are away, which reads as a crash — and since nothing repaints while idle, the decay just sits there until a keypress forces a full repaint. LPM saved only the panel booster anyway; the `delay(30)` is where the power actually goes. It also deliberately does **not** touch the CPU frequency: below 80MHz the ESP32-S3 takes the PLL down and kills USB-CDC, and with it the serial console. Two traps in the "is a task running" guard, both of which made it look permanently busy: a missing `app["task"]` stringifies to `"null"`, not `""`, and `SYNC_START` is **0**, which is also what an absent `sync_state` reads as. **Rest screen** (`rlcd_draw_rest` in `display_RLCD.cpp`, so it works from any screen): the deck mark (`RLCD_drawDeviceMark`, shared with About — the mark is a deck wearing the Happy Mac's face, its smile a plotted arc since three segments read as a chevron at this size) beside the open file's title, and live word count — mark left, text right, the same arrangement About uses. There is no battery reading to put beside them: the cell goes through a charger/step-up module with nothing on an ADC. The wordmark is Latin-only now: the home title bar reads "katibOS" and neither screen paints كاتب, so the only كاتب left in the tree is the ordinary word inside the AI prompt. Opt-in via `config.screensaver` — Options → **Screensaver**, **off by default** — this panel is reflective, so there is no burn-in to prevent and the card costs you the sight of your own text. While it is up `display_RLCD_loop` **returns before dispatching to any screen**, or the live screen repaints straight over it (and skipping the pushes is the point of resting anyway). **Screensaver and its wake are verified on rev_8** (2026-08-16).

- **There are no sleep tiers, and adding them back needs a serial console first.** A `Sleep` (light) and `Shut down` (deep) pair lived here until the build after 1.14.6, staged off the same idle timer, waking on the matrix via `esp_sleep_enable_ext1_wakeup(ANY_HIGH)` with `keypad_prepare_wake()` inverting the scan — columns held HIGH as outputs, rows `INPUT_PULLDOWN`. Their **first run on real hardware** (2026-08-16) failed: light sleep entered correctly and drew its card, and **no keypress ever brought the chip back** — the only way out was pulling the cable. Three fixes were tried on-device and none worked: `gpio_hold_en` on the columns (six of the nine are digital-only pads at GPIO 39–48, so they stop driving when the domain powers down); switching light sleep from the digital `esp_sleep_enable_gpio_wakeup()` path to ext1; and configuring the rows through `rtc_gpio_*` since `pinMode`'s pulldown does not follow a pad into the RTC mux. The last attempt woke the device into a garbled state that typed into the open document — `gpio_deep_sleep_hold_en()` latches **every** digital pad, and this board's display SPI lines (SCLK 12, MOSI 11, CS 10, DC 46) are digital pads too. All of it was debugged blind — but **not because the console was unavailable**: it works over the board's CH343 bridge and always did (verified 2026-08-19, see below). The blindness was a wrong assumption, not a missing capability, so whoever picks this up starts with a working log. Removed rather than left off-by-default: the failure mode (device looks dead, writing session over) is the worst one this product has, and the tier that failed was also the one with the least to give, since the `delay(30)` is where the power saving actually is. **The console is available; use it from the first line of wake code.**
- **Sync** (`service/Sync/`) — Drive (Apps Script) or git provider (`config.sync.git`, token on-device). **OTA** (`service/Updater/Ota.cpp`) — Wi-Fi manifest at `KATIBOS_UPDATE_URL` (set in `platformio.ini` → `firmware/latest.json` in this repo); the bin download follows GitHub's cross-host redirect manually with a `setInsecure()` TLS client. The release asset is `katibOS-journal.bin` on the `alfarhan/katibos-journal` releases (v1.13.0 and earlier: `firmware_microjournal.bin` — the manifest names whichever the release actually carries, so the two must be changed together or OTA 404s). The whole flow runs unattended (Connecting → Redirecting → Preparing storage → Downloading N% → Installing → Update installed), with Enter only at the end to reboot. Two traps behind that: **`Menu_render` only runs a sub-screen when something marked the menu dirty**, so `Ota_render` calls `Menu_clear()` while it has deferred work pending — without it the screen sat on "Connecting..." until an unrelated keypress happened to trigger the next render. And since nothing renders while `ota_apply()` holds the loop, every stage label pushes its own repaint (`setStage` → `g_redraw`). Download and flash are one phase, not two — `Update.writeStream` writes each chunk as it arrives — so the percentage is labelled "Downloading" and only `Update.end` (verify + switch boot partition) is "Installing".
- **UI kit** (`display/RLCD/display_RLCD.h`) — the shared drawing vocabulary; use these instead of hand-rolling a screen. `RLCD_drawTitleBar` (striped bar, title in a cleared tab — `Menu_drawHeader` calls it, so *no screen draws its own header*), `RLCD_drawWindow` (shadow + frame + optional title bar: dialogs and info panels), `RLCD_drawHintBar` (key in plain text + verb on an inverted chip), `RLCD_drawScrollbar`, `RLCD_drawShapedLabel` / `RLCD_shapedLabelWidth` (Arabic-safe label, measure-then-place). Conventions: verbs uppercase, `^` = Ctrl/Fn, no brackets around keys, no screen draws a divider under the header. Hint bars: confirm dialogs put theirs under their own window; a screen whose keys exist *nowhere else* (Sync, Update, Wi-Fi) pins a footer instead — divider at y=276, bar centered at y=296, list scrollbars ending at 266 to clear it. Screens whose list fills the height (Language, Help, and the home screen's cards) carry the key in each row and get no footer.
- Design/context docs: `firmware/doc/KATIBOS.md`, `SYSTEM_OPTIONS.md`, `DEVICE_SYNC.md`.

## Menu keys

**FILES and SETTINGS are one screen** (`MENU_HOME`), split by a **vertical** rule at `SPLIT_X`: the file list left, the settings cards in a single column right. `→` crosses to the cards and `←` comes back (`TAB` does either); the arrows otherwise stay inside whichever half holds the cursor. The divider is vertical because a horizontal one spent its height on the cards and left the list 3–4 rows — on the screen you live in; vertical keeps ~9. `MENU_SETTINGS` still exists as a state — a dozen sub-screens return to it — but `Menu_render` folds it into `MENU_HOME`, so back always lands here without rewriting those callers. `Ctrl+.` focuses the cards via `Home_focusCards()`. Each list row ends in the file's **word count** — it replaced the sync mark, which at 216px is the only way both fit — and the title is trimmed by measurement (`Home_fitTitle` shrinks the cap until `RLCD_shapedLabelWidth` clears the count column) rather than a fixed character cap, since the count's width moves with the number and an Arabic glyph isn't a Latin one. The list also gets a classic Mac scroll bar (`Home_drawMacScroll`: stippled track, arrow box each end, thumb sized to the visible fraction, nothing when it all fits). Cards are mark-left / name-right, one per row, sized by `Home_cardH()` from however many are actually listed (eight at most — Sync comes and goes with the config). **Icons scale** — `drawActionIcon` takes a size and every icon is drawn on a 28-unit grid through `S(v)`, so `Settings_drawCard` picks 28/20/16 from the card height rather than forcing the card to fit a fixed 28px mark; a fixed icon ran straight through the frame once the list grew. Widths are measured, not guessed: "Preferences" is 98px via `getUTF8Width`, which is what sets the column at 146. `Settings.cpp` is now the card **model** only (list/labels/keys/icons/dispatch, exposed for Home) — its setup/render/keyboard entry points, `Menu_drawTabs` and `drawDeckIcon` are gone with the tab strip.

One letter per destination, the same everywhere it's handled (file list, settings cards, Help): **O** Options · **L** Language · **W** Wi-Fi · **S** Sync · **D** Drive · **U** Update · **H** Help · **A** About · **T** Restart (on the cards, confirmed). File list: `ENT` open · `R` rename · `X` delete · `N` new · `TAB` cross to the cards. From the editor, **Ctrl+,** opens Preferences and **Ctrl+.** the settings cards (both via a one-shot `menu.goto` that `Menu_setup` consumes).

**Help's tables are a contract the matrix must honour.** rev_8 has no Ctrl in the firmware sense — Ctrl, Win, both Alts and Fn are *all* the ALT layer key (17) — so any chord `keyboard.cpp` gates on a real `ctrl` is unreachable here, and several were advertised on the Help screen while doing nothing: `^/`, `^G`, `^U` (fixed in 1.13.0), then `^L/R`, `^Up/Dn`, `^Home/End`, `^Sh+U`. When adding a shortcut, wire the **matrix** path, not just the HID one, and audit Help against `keyboard_keypad_68_get_key` rather than trusting it. Two traps in that function: a shifted chord resolves on **layer 3, whose letter table is uppercase**, so `key == 'u'` never matches with Shift held (use `'U'`, and check the shifted chord *before* the unshifted one); and codes the keypad emits only on `KEY_JUST_PRESSED` must not be handled behind `if (!pressed)` in `WP_keyboard` — Esc arrives on both edges, these arrive once. **Caps Lock** (16, was dead on all four layers) toggles the typing layout, read off layer 0 before layer resolution so it fires whatever else is held; `Fn+Space` still does it too. **Ctrl+,** / **Ctrl+.** reach Preferences / the settings cards from the editor, and Esc there returns to the editor via `menu.prefs_from_editor`.

Two traps this key map already walked into: a screen's own back key shadows a list letter (`B` used to eat `[B] Belgian` in Language — Esc/Left are the back keys there now), and the file list's `X`-for-delete exists so `D` can stay the global Drive jump. Keep `Help.cpp`'s tables in sync with the handlers — they are the only user-facing documentation of these keys, and its row pitch is set by the JUMP column clearing the callout box at y=228, so adding a destination means re-checking that.

The Settings grid shows each card's key by **underlining that letter in the card's own name** (`drawKeyedLabel`) instead of printing the key separately — so every card's key must actually occur in its label, matched case-insensitively on the first hit (`D` → "USB **D**rive", not the U). Layout and Sync provider are rows inside Options (there is no Time zone setting — it was removed); About is a card of its own on the grid, since it's a destination rather than a setting. The keyboard-layout screen is called **Layout** everywhere — Options row, its own header, Help's `L`, and `^Space` in the editor — not "Language", which reads as UI language rather than key mapping. Preferences groups its rows with plain rules and no section text, so the row order *is* the grouping: editor rows, then power (Power save, Screensaver), then Layout, Sync provider, Factory reset.

## Cutting a release

`ota_check()` compares the manifest's `version` to `KATIBOS_VERSION` as a plain string — not newer/older — so the manifest must always name the version that's actually in the release, and the bins must be built *after* the bump.

1. Bump `KATIBOS_VERSION` in `firmware/src/app/app.h`.
2. `pio run -e microjournal`.
3. **Push `main` first**, then `gh release create vX.Y.Z --title "katibOS X.Y.Z" --notes "…"`. `gh` tags the *remote* default branch, so releasing before pushing tags whatever the remote last saw - every tag up to v1.15.0 is one commit behind its own release and `git show v1.15.0:...app.h` reports the previous version. The bins are correct; the tags are not. with the bin renamed to `katibOS-journal.bin` (the manifest points at that exact asset name). Releases up to and including v1.13.0 used `firmware_microjournal.bin`, so don't "fix" an old manifest to the new name — the asset behind it still carries the old one.
4. Point `firmware/latest.json` at the new version + asset URL, commit, **push to `main`** — devices fetch it from `raw.githubusercontent.com/.../main/`, so an unpushed manifest ships nothing.

A device only offers an update when its own version string differs, so to test the OTA path flash the *previous* version over USB first, then release the new one.

## Notes

- `platformio.ini`'s `build_src_filter` is an explicit **allowlist** — a new `src/service/<X>/` directory does not compile until `+<service/X/*>` is added, and the failure is a link error, not a missing-file one. The emulator's `FW_CPP` list in `emulator/Makefile` is the same trap.
- Version string: `firmware/src/app/app.h` (`KATIBOS_VERSION`) — bump when cutting a release.
- **A full chip erase deletes the writing.** `pio run -t erase` wipes the `storage` FAT partition (8MB at `0x7F0000`, see `partition_esp32s3_rev8_16mb.csv`) along with `nvs` — every document, plus `config.json` with the Wi-Fi credentials, sync token and Gemini key. Offer USB Drive mode (**D**) to copy files off first, and never treat "erase the chip" as consent to losing them unless that cost was stated.
- **`_log()` DOES reach the Mac — the console works (verified 2026-08-19).** A full boot log was captured over `/dev/cu.usbmodem5C4C1398481` at 115200, banner included: `katibOS 1.15.0 on MicroJournal`. The port is a **WCH CH343 USB-to-UART bridge** (VID:PID `1A86:55D3`), not the S3's native USB-Serial-JTAG (which would be `303A:…`), so UART0 *is* wired out on this board and `ARDUINO_USB_CDC_ON_BOOT` is irrelevant — nothing needs fixing. The earlier note here claimed zero bytes and blamed the missing CDC flag; that was wrong, and it is the reason the sleep/wake work was abandoned as "blind". Read it with pyserial (`serial.Serial(port, 115200)`, drop RTS to reset and catch the banner) rather than `pio device monitor`, which needs a TTY — under a captured shell it dies in `termios.tcgetattr`, so use `stty -f <port> 115200 raw` plus `cat`. Boot prints `katibOS <version> on <board>`, the quickest way to confirm which build is running. Let **exactly one process** hold the port: two readers split the byte stream into half-lines, and opening it toggles DTR/RTS, which resets the board. `esp_core_dump_flash: No core dump partition found!` prints on **every** boot, and `rst:0xc (RTC_SW_CPU_RST)` on its own is *not* evidence of a crash — a normal `ESP.restart()` prints exactly that.
- OTA is served from this repo (`firmware/latest.json`). A device can still override the manifest via `config.json` `update.url`; a stale `alfarhan/micro-journal` URL is treated as dead and falls back to `KATIBOS_UPDATE_URL`.
- Global prefs: RTL-first (logical CSS props), Arabic when writing Arabic, terse output, comments only where the *why* is non-obvious.
